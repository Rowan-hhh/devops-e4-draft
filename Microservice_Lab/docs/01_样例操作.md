# 样例操作

## 1. 启动服务

用 SSH 登录本组云服务器。服务器需有 Docker Engine、Docker Compose、Python 3 和 `unzip`。用 SFTP 将 `Microservice_Lab.zip` 上传到服务器用户主目录。以下命令在服务器终端整块执行。

```bash
mkdir -p "$HOME/devops-materials"
unzip -n "$HOME/Microservice_Lab.zip" -d "$HOME/devops-materials"
cd "$HOME/devops-materials/Microservice_Lab"
docker compose version
python3 scripts/lab.py init
```

在实验包根目录依次执行以下命令。`init` 会生成 `.env` 和 Grafana 登录密码。已有 `.env` 时继续使用里面的配置。若默认端口已被占用，先修改 `.env` 中的端口，再启动服务。

```bash
docker compose config --quiet && docker compose up -d --wait --wait-timeout 90
mkdir -p work
docker compose ps | tee work/compose-before.txt
docker compose images | tee work/images.txt
python3 scripts/lab.py target 1
```

首次启动会拉取镜像。`api` 和 `worker` 应显示 `healthy`，最后一条命令输出 `lab-worker up=1`。API 通过 Compose 服务名 `worker` 调用下游。

## 2. 打开监控页面

在自己的电脑另开一个终端，执行下面的 SSH 转发命令。先替换服务器用户名和地址。若第一步改过服务器端口，同步替换 `-L` 每项最后一个端口。

```text
ssh -N -L 19090:127.0.0.1:19090 -L 13000:127.0.0.1:13000 用户名@服务器地址
```

|页面|看什么|
|---|---|
|`http://localhost:19090/targets`|`lab-api` 和 `lab-worker` 的采集状态|
|`http://localhost:13000`|在 Dashboards 打开「微服务实验」，查看 Worker 采集状态、任务计数和平均耗时|

Grafana 用户名为 `admin`，初始密码在服务器实验目录 `.env` 的 `GRAFANA_ADMIN_PASSWORD` 中。首次登录若提示修改密码，按页面提示操作。截图时保留图表、时间范围和图例。

## 3. 正常任务

回到服务器终端，在实验包根目录整块执行。

```bash
python3 scripts/lab.py run normal
```

预期输出 `PASS normal SUCCEEDED attempts=1`。脚本用同一个幂等键提交两次，分别保存在 `submitted.json` 和 `repeated.json`，应返回同一个 `job_id`。目录以屏幕显示的 `EVIDENCE_DIR` 为准。`report.json` 应记录 `main.o` 缺少 `config.h`、多声明 `unused.h`，且文件 SHA256 与状态响应中的清单一致。

## 4. 停止下游并恢复

先完成正常任务。在样例目录整块执行下面的命令。

```bash
date -Is | tee work/worker-stopped-at.txt
docker compose stop worker && python3 scripts/lab.py target 0 && python3 scripts/lab.py run down
```

预期输出 `lab-worker up=0` 和 `PASS down FAILED attempts=3`。状态文件的错误码为 `DOWNSTREAM_UNAVAILABLE`。这里的 `PASS` 表示故障任务按预期失败。先在 Grafana 确认采集状态降为 `0`，并看到失败任务计数上升。

整块执行下面的命令恢复 Worker。

```bash
docker compose start worker && python3 scripts/lab.py target 1 && python3 scripts/lab.py run recovered
date -Is | tee work/worker-recovered-at.txt
docker compose ps | tee work/compose-after.txt
```

预期输出 `lab-worker up=1` 和 `PASS recovered SUCCEEDED attempts=1`。对比恢复前后的任务和报告。停止再启动用于验证人工恢复和业务重新可用。

完成上面三个场景后，可运行 `python3 scripts/lab.py run timeout`。Worker 会在每次调用休眠 3 秒，API 的每次读超时为 2 秒，最多尝试 3 次。预期 `PASS timeout TIMED_OUT attempts=3`，错误码为 `DOWNSTREAM_TIMEOUT`。

## 5. 留存日志和指标

整块执行以下命令，按提示输入故障任务的实际 `job_id`。

```bash
docker compose logs --no-color --timestamps api worker > work/services.log
read -r -p '故障任务 job_id: ' JOB_ID
if [ -n "$JOB_ID" ]; then
  grep -F -- "$JOB_ID" work/services.log | tee work/failure-job.log
fi
```

故障日志应找到 3 次 `worker_call`、对应的错误和 1 次 `job_finished`。正常和恢复任务应能在 API 与 Worker 两边找到相同的 `job_id` 和 `trace_id`。Grafana 截图选择覆盖三阶段的时间范围。`up` 表示抓取状态，业务结果看任务终态和 `lab_jobs_total`。

保存文件后，从实验包根目录执行 `docker compose down` 关闭实验。该命令保留监控卷，API 进程内的任务状态已由实验脚本保存到 `work/`。
