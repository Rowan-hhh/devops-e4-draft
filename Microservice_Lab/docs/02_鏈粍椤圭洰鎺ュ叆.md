# 本组项目接入

在本组项目中重复样例的操作顺序。使用一组真实 Git 提交，保留任务请求、业务指标、阶段日志和验证结果。

## 1. 部署与监控

1. 在本组 Compose 目录执行 `docker compose up -d` 和 `docker compose ps`。逐项核对任务入口、下游服务和健康检查地址。
2. 在本组业务服务暴露 `/metrics`。至少记录按结果区分的任务计数和耗时，通过 `job_id`、`trace_id` 在日志里关联同一任务。
3. 在同一 Compose 网络内，将本包 `monitoring/prometheus.yml` 中的 `api:8080`、`worker:8080` 换成本组服务名和容器端口，并将监控服务接入本组 Compose。若项目已有监控，直接在原配置添加本次业务目标。面板查询使用实际暴露的指标名。[Prometheus 抓取配置](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)
4. 只在本组实验环境停止实际参与任务的下游服务。记录故障任务的终态、阶段、错误码和重试次数，恢复健康后用新幂等键提交同一输入。已有 Elastic Stack 的组可在 Kibana 中按同一编号展示集中日志。[Elastic 日志接入](https://www.elastic.co/docs/solutions/observability/logs/ecs-formatted-application-logs)

## 2. 用 E12 接口运行真实项目

选择一个能说明缺失依赖如何引入和修复的提交范围。向本组 E12 接口提交仓库、基线 commit、目标 commit、候选 Dockerfile 和验证条件。保留完整的 40 位 SHA。

若沿用课程 E12 包，先按 E12 手册部署接口，将本组项目与候选文件放在该接口可访问的位置，并填好 `real-request.json`。它是包含 `mode: e12`、`repo`、`base`、`target`、`candidate` 等字段的输入文件。路径按 E12 服务端的实际目录填写。

在服务器的微服务实验包根目录执行。把 E12 输入文件复制到 `work/real-request.json`，若 E12 使用了其他监听端口，替换 `8080`。

```bash
python3 scripts/project.py work/real-request.json --port 8080
```

脚本提交请求、轮询终态，并保存五个阶段的报告和补丁。它核对任务编号、基线与目标提交、报告 SHA256 和修复结果。终端显示的 `EVIDENCE_DIR` 是本次报告位置。使用自定义接口的组可按下表留存同样的证据。

|阶段|需要核对的结果|
|---|---|
|DRAFT|构建和程序验证成功，保存实际镜像标识|
|BuildChecker|从基线提交取得实际图和声明图，记录检测环境|
|EChecker|目标提交的增量报告能说明新增或消除的 MD/RD|
|MDFixer|读取本次目标提交的 MD 报告，生成 Patch 并保存输入报告引用|
|复验|补丁通过构建和测试，原有 MD 消除，检查是否产生新错误|

在实验记录填入每阶段实际使用的镜像或环境。若下游未用 DRAFT 环境，写明该交接尚未验证。`project.py` 核对任务和产物关系，镜像交接还要看阶段运行记录。

## 3. 验证回滚

使用本组已有的补丁拒绝、测试失败或回滚路线，保留失败前后的仓库状态、拒绝日志和补丁。核对原仓库的提交和工作区。将本次故障和恢复记录写进 `templates/实验记录.md` 的副本。
