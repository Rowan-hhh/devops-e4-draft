# 微服务实验：可观测性、容错、编排与系统集成

在本组云服务器部署项目，用一组真实 Git 提交完成集成任务。保存正常运行、服务中断和恢复三个阶段的状态、日志和指标，再核对修复产物。

|部分|实验任务|通过条件|
|---|---|---|
|编排|用 Docker Compose 启动业务服务及监控组件|服务通过健康检查，依赖可以通过服务名访问|
|可观测性|抓取业务指标，关联同一任务的阶段日志|面板能观察到任务结果变化，日志能定位失败阶段|
|容错|停止一个下游实验服务，观察失败后恢复服务|任务在规定时间内结束或执行有限重试，恢复后新任务成功|
|系统集成|用本组项目贯通构建、检测、修复、复验|记录实际提交、统一任务编号、阶段产物和最终结果|

## 1. 编排与健康检查

**任务**　进入本组已有 Compose 部署文件所在目录。选择一个有明确下游依赖的任务，同时确认实际服务名、对外任务入口、健康检查地址、指标地址和产物目录。

**操作**　以下命令在 SSH 登录后的服务器终端整块执行。

```bash
mkdir -p evidence/microservices
date -Is | tee evidence/microservices/start-time.txt
docker compose config --quiet && docker compose up -d && docker compose ps | tee evidence/microservices/compose-before.txt
docker compose config --services
```

使用各组实际配置中的 `healthcheck` 和业务健康接口检查就绪情况。`docker compose ps` 显示 `Up` 只表示容器在运行。服务有启动依赖时，为被依赖服务配置 `healthcheck`，并在依赖方使用 `depends_on` 的 `condition: service_healthy`。运行中的依赖故障由业务超时、重试和状态处理验证。[Compose 启动顺序与健康检查](https://docs.docker.com/compose/how-tos/startup-order/)

核对以下三项后开始提交任务。

- 业务服务能访问所需依赖，Compose 内部连接使用服务名和容器端口。
- 检查预期对外接口能返回成功响应，监控页面需要从电脑访问时使用 SSH 端口转发。
- 若只有 E11–E12 的本地编排入口，先确认它的 `/health` 和 `/v1/jobs` 能工作。该入口可以验证任务串联。下游停机实验需要选择本组实际部署的下游服务，或使用本组已有的可控故障开关。

**保存**　Compose 文件、服务列表、健康检查响应和启动日志。提交配置样例时保留变量名，实际凭据放在部署环境里。

## 2. 指标与日志

### 2.1 Prometheus 与 Grafana

**任务**　采集业务服务的指标。在本组程序中通过 `/metrics` 暴露指标，或使用对应组件的 exporter。附件里的 Prometheus 自抓取和 node_exporter 可以用来验证采集配置；本次面板还要看到本组服务的业务任务变化。[Prometheus 抓取配置](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)

Prometheus 与被监控服务在同一 Compose 网络时，抓取地址写成 `服务名:容器端口`。例如业务服务名为 `worker`、容器端口为 `8080`，则在现有 `scrape_configs` 下增加以下条目并按本组配置替换两项。

```yaml
  - job_name: 'devops-worker'
    metrics_path: /metrics
    static_configs:
      - targets: ['worker:8080']
```

在 Prometheus 的 Targets 页面核对业务目标显示 `UP`。在 Grafana 配置 Prometheus 数据源。两者在同一 Compose 网络且服务名为 `prometheus` 时，数据源 URL 可用 `http://prometheus:9090`。保存后先查业务目标的 `up`，再添加任务量、失败量和耗时图。[Grafana 数据源配置](https://grafana.com/docs/grafana/latest/datasources/prometheus/configure/)

|建议图表|数据来源|看什么|
|---|---|---|
|采集状态|`up{job="devops-worker"}`，按实际 job 名改|采集正常、目标中断和恢复|
|任务结果|按成功、失败、超时统计的任务计数器|故障窗口内失败或超时次数增加|
|阶段耗时|阶段耗时指标，或请求延迟直方图|比较正常、故障和恢复后的耗时|

PromQL 按实际暴露的指标名编写。`up=1` 表示 Prometheus 抓取成功，业务是否成功以任务终态和产物为准。故障期间至少等到页面完成一次有效的故障采样再恢复，并选择覆盖三个阶段的时间范围。`job_id`、`trace_id` 放在日志中，指标按服务、阶段和结果等有限取值聚合。[Prometheus 配置与抓取周期](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)

### 2.2 日志定位

**任务**　提交一条业务任务，记下返回的 `job_id`，沿各服务日志找到该任务的开始、阶段结果和结束。统一字段建议使用 `timestamp`、`service`、`level`、`job_id`、`trace_id`、`stage`、`event`、`duration_ms`。失败事件追加 `error_code` 和重试次数。

**操作**　完成任务后，在同一 Compose 目录整块执行，按提示输入实际 `job_id`。

```bash
read -r -p '输入业务任务 job_id: ' JOB_ID
if [ -n "$JOB_ID" ]; then
  docker compose logs --timestamps --no-color > evidence/microservices/services.log
  grep -F -- "$JOB_ID" evidence/microservices/services.log | tee evidence/microservices/job-trace.log
fi
```

若某个阶段只记录 `trace_id`，用同样方法按该值继续检索，并在报告中说明每条日志属于哪个服务。`job_id` 用来找任务，`trace_id` 用来串起服务调用。

**集中检索**　已部署 Elastic Stack 的小组，可通过 Elastic Agent 采集应用日志，在 Kibana Discover 按 `job_id` 或 `trace_id` 检索。按本组 Elastic/Kibana 版本选择兼容的采集集成，使用本环境生成的注册信息。展示同一任务的连续阶段和故障日志。[Elastic 日志采集说明](https://www.elastic.co/docs/solutions/observability/logs/ecs-formatted-application-logs)

**保存**　业务 Targets 页面、Grafana 面板或导出配置，以及按任务筛选后的日志。若使用 Kibana，同时保存检索条件和结果。

## 3. 容错与恢复

**任务**　暂时停止本组实验环境中的一个下游服务。用同一组项目输入分别执行故障前、故障中、恢复后三次任务，每次新任务使用新的幂等键。

1. **故障前**　提交一次正常任务，记录任务编号、终态和耗时。
2. **故障中**　在服务器终端执行 `docker compose stop 实际下游服务名`，先把中文部分换成自己的服务名。再次提交相同业务输入，记录失败阶段、错误码、任务终态和发生时间。停止的服务须是这条业务任务实际调用的下游。
3. **恢复后**　执行 `docker compose start 同一下游服务名`，等健康检查恢复，再提交任务。记录恢复时间和最终产物。用同一个时间范围展示故障前、中、后的指标。

|检查项|通过条件|
|---|---|
|超时与重试|任务按配置超时并返回可定位的错误，或在限定次数内重试后成功|
|状态正确|失败任务进入 `FAILED` 或 `TIMED_OUT` 等约定终态，不长期停在 `RUNNING`|
|重复提交|相同请求和同一幂等键返回同一任务编号，通过日志确认没有重复构建；新一轮重跑按接口约定用新键|
|恢复|服务就绪后，新任务取得正确终态并生成有效产物|
|补丁回滚|另跑一次补丁验证失败场景，保存拒绝或回滚记录，核对原仓库的提交与工作区保持原样|

`stop` 后 `start` 验证的是人工恢复及业务重新可用。若项目实现自动重启或自动重试，再单独记录恢复触发条件、重启次数或重试日志。

**保存**　故障前、中、后的状态响应、日志和面板，记录执行命令、时间及恢复方式。

## 4. 系统集成验证

**输入**　本组项目仓库、基线与目标提交的完整 SHA、构建候选及验证条件。选择一个能够说明缺失依赖如何被发现和修复的提交范围。仅用于预跑的生成样例在报告里标为样例。

|环节|交给下一环的内容|核对项|
|---|---|---|
|DRAFT|可构建镜像标识、Dockerfile、构建日志引用|实际构建及程序运行通过，记录供后续使用的镜像或环境标识|
|BuildChecker|基线实际依赖图、声明依赖图及报告引用|基线提交和构建环境与请求一致|
|EChecker|目标提交的增量图及 MD/RD 报告引用|说明新增或消除的错误，保留目标提交标识|
|MDFixer|补丁引用及验证结果|消费本次目标提交的 MD 报告，核对版本，生成并验证补丁|
|重新构建与检测|修复后的构建、测试及重检报告|构建和测试成功，原有 MD 消除，并核对是否出现新问题|

通过本组实际任务入口提交上述输入，保存请求、任务查询响应、终态及产物清单。用 `job_id` 对齐结果，用 `trace_id` 对齐日志。提交基线和目标的 SHA，标出每份报告属于哪个提交。记录下游实际使用的环境标识，确认与 DRAFT 的环境交接一致。现有 E12 路线若仍采用集中编排或固定样例，按实际部署记录；组间接口、环境交接和本组数据的运行结果分别核对。
